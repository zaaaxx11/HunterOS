# OPEN-PROBLEMS.md — what the schema still cannot do

Post-PR-1 state. The evidence ladder, anti-tamper triggers, computed wave
counts, reaudit summaries, and db fingerprint are in. These are the holes
that remain, ordered by how badly each one lies.

---

## P1 — Verifier events are self-attested [PARTIALLY CLOSED by PR-6]

**Hole:** `hunt verify` writes a `verifier_pass` event, but the same operator
types it in the same terminal that promotes the finding. The DB cannot tell a
real fork run from a typed sentence.

**Why unsolved here:** single-process, single-operator, stdlib-only. Trust
cannot be minted inside the same session that spends it.

**Mitigation today:** verifier role discipline (`soul/roles/verifier.md`);
the event at least leaves an auditable row with role + artifact type + body.

**Real fix candidates:**
- **PR-6 (bridge) — closed (the claim-gate half):** the engine-side claim gate
  (`bridge/claim_gate.py`) now makes unbacked PROVEN/EXPLOITABLE claims fail
  the turn (exit 2) unless the hunt db backs them with proven-live rows, so
  lying about results is mechanically expensive, not just discouraged. What
  remains open: the verifier event itself is still self-attested by the same
  operator — cross-process attestation stays a candidate.
- Cross-process attestation: verifier runs in a separate process owning a
  separate DB; `promote_finding` cross-checks that DB instead of trusting a
  same-session event. (Design needed; two-DB sync is new surface.)

## P2 — PoC content authenticity

**Hole:** PR-1 enforces a *different* sha256 per ladder step. A diligent liar
writes a new garbage file per step. Hash distinctness proves effort, not truth.

**Why unsolved here:** judging whether a file is a real PoC requires running
it or reading it — that is execution, not storage.

**Mitigation today:** empty files rejected; distinct hash + fresh evidence_ref
required; verifier event must exist before proven-live.

**Real fix candidates:**
- Artifact registry: `hunt verify` stores a *snippet* of real tool output
  (fork receipt header, explorer JSON) in `events.detail`, min-length and
  structure-checked per artifact type.
- tx_hash linkage: for `tx_hash` artifacts, store the hash and require the
  evidence_ref to reference the same hash (consistency check, still not truth).

## P3 — Self-reported scoring inputs

**Hole:** `ev_score`, `tvl_usd`, `age_days` are typed by the operator. Wrong
inputs steer the economic stop decisions (SCORE gate, two-empty-waves rule).

**Why unsolved here:** the DB validates ranges, not reality.

**Mitigation today:** score gate only fires in the scoring phase; all claims
logged in events. Phase exit gates (PR-2) now require artifacts per phase —
the *empty-phase speedrun* hole is closed; the remaining P3 hole is only the
truthfulness of typed numbers. PR-4's finding `--action` and RoE `--hosts`
are also self-declared; the DB enforces the promote gate and flags
retroactive RoE changes (`hunt status`), not truth.

**Real fix candidates:** score inputs as linked findings with their own
evidence, or an external pricing source (breaks stdlib-only — parked until
the app layer earns dependencies).

## P4 — Reports can be edited after generation [CLOSED by PR-5]

Closed: `hunt verify-report <file>` recomputes the sha256 of the report body
(everything before the footer comment line) and compares it against the
`hunt-report` footer. A hand-edited report no longer reads fine — verification
refuses it with `BLOCKED: report has been tampered with`, and files without a
footer (not generated by `hunt report`) are refused too, so the check cannot
be bypassed by stripping the footer.

---

## P5 — HUNT_DB can be swapped mid-story [CLOSED by PR-5]

Closed: `hunt project bind` writes a `.huntos-project` lock file (full db_id +
bind timestamp) into the working directory and records a `project_rebound`
event in the db it binds to. Every CLI run re-checks the lock against
`HUNT_DB`: a mismatch blocks all write commands with `BLOCKED: ... rebind
first: hunt project bind`. Read-only commands (`status`, `verify-report`) pass
with a hard warning, and the `project` group bypasses the lock so a deliberate
switch can always be repaired.

---

## P6 — klass is still free text [CLOSED by PR-3]

Closed: the klass allow-list lives as DATA in a `taxonomies` table (9
researched classes + the `Unknown` quarantine class, seeded on connect) and is
trigger-guarded on insert and update — raw-SQL cheats abort. New classes are
born only at retro via `hunt klass add`, so growth never needs a schema
migration.

---

## P7 — Legacy DBs do not migrate

**Hole:** pre-PR-1 databases (no `poc_sha256`, no `meta`, no `wave_id`,
no CHECKs) keep working without the new guarantees — `CREATE TABLE IF NOT
EXISTS` never alters existing tables.

**Severity today:** zero real hunts have run; nothing to migrate.

**Real fix candidate:** `hunt migrate` (PRAGMAs + table rebuild) or declare
"delete and restart" acceptable. Decide before the first real hunt.

---

## P8 — `evidence_ref` has no semantic binding [PARTIALLY CLOSED by PR-6]

**Hole:** refs must differ per step but are otherwise opaque strings; nothing
ties a ref to the artifact it describes.

**PR-6 partial closure:** the bridge routes all claims through hunt CLI
commands, so refs are produced at the moment of evidence (`hunt verify`,
`hunt finding promote` with the artifact in hand), not typed from memory
after the fact. Full semantic binding — an explorer cross-checking that the
ref really describes the artifact — remains open.

---

## P9 — Taxonomy cleanup tooling (rename/merge)

A class added at retro with a typo (e.g. "Brdge") is permanent-ish: there is
no rename or merge command. Deliberately deferred — merging classes needs
re-tagging history and lesson re-binding. Candidate for the app layer once
real hunts produce real taxonomies.
